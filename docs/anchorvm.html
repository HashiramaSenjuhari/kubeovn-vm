Kube-OVN · libvirt · network only

anchorvm VMPorts

Create a VMPort in Kubernetes and your libvirt VM gets a network card on a Kube-OVN subnet: the same subnet as your pods, an IP from Kube-OVN, no duplicates, and a correct cleanup when you delete it.

anchorvm never creates, starts, stops or deletes VMs, and never touches disks or storage. Your platform keeps owning the VM. anchorvm owns only the VM's network card: IP, MAC, OVN port, DHCP, security groups and the tap device. It runs on stock, unmodified Kube-OVN v1.16.0, without KubeVirt.

The idea

Kube-OVN manages pods very well but knows nothing about VMs outside Kubernetes. So for every VM network card, anchorvm creates a stand-in pod that never runs. We call it the anchor pod.

Kube-OVN treats the anchor like any pod. It gives it an IP and MAC from its own allocator, so duplicates are impossible. It creates the OVN port with DHCP and security groups, keeps that port safe from its garbage collection, and frees the IP when the anchor is deleted.

The real VM then plugs a tap into that OVN port and asks DHCP for an address. It gets the anchor's IP. The VM is wearing the pod's network identity.

Three pieces

Kubernetes resourceVMPortWhat you ask for: a NIC on subnet X for a VM on hypervisor Y. Optionally a fixed IP, MAC and security groups.
Deployment in the clusterControllerCreates the anchor pod, waits for Kube-OVN to allocate, writes IP, MAC and port name into the VMPort status, and deletes things in the safe order.
systemd on each hypervisorAgentFor VMPorts of its own host only: creates the tap, plugs it into OVN, optionally hot-plugs it into your VM, and reports back.

Lifecycle

stateDiagram-v2
  [*] --> Pending: VMPort created
  Pending --> NetworkReady: Kube-OVN allocated IP, MAC, port
  Pending --> IPConflict: requested IP already in use
  NetworkReady --> Ready: agent plugged tap, OVN installed it
  Ready --> Unknown: agent heartbeat stale
  Unknown --> Ready: agent back
  Ready --> Deleting: VMPort deleted
  NetworkReady --> Deleting
  IPConflict --> Deleting
  Deleting --> [*]: NIC unplugged, then anchor deleted, then IP freed

When your platform stops, starts, reboots or deletes the VM, nothing changes for the VMPort. The tap is persistent and the IP stays reserved until you delete the VMPort.

Deletion is strictly ordered. The agent unplugs the NIC and removes the tap first, then the controller deletes the anchor, then Kube-OVN frees the IP. An IP is never handed to someone else while a VM may still be using it. If the agent cannot be reached, the VMPort shows DeletionBlocked and waits for an admin.

Using it

TapOnly (default)

anchorvm creates the tap. Your VM's libvirt XML references it.

apiVersion: anchorvm.io/v1alpha1
kind: VMPort
metadata: {name: web1-nic0, namespace: team-a}
spec:
  hypervisor: os-aio
  network:
    nad: shadow-lab/shadow-net   # Kube-OVN NetworkAttachmentDefinition
    subnet: shadow-subnet
    # ip: 10.240.0.20            # optional fixed IP
    # securityGroups: [web]      # optional, changeable later
$ kubectl get vmport -n team-a
NAME        HYPERVISOR   PHASE   IP            MAC                 TAP
web1-nic0   os-aio       Ready   10.240.0.20   3a:aa:a7:21:c0:96   av4f1c2d9e0ab

Put this in the VM's XML, with the MAC and tap from the status:

<interface type="ethernet">
  <mac address="3a:aa:a7:21:c0:96"/>
  <target dev="av4f1c2d9e0ab" managed="no"/>
  <model type="virtio"/>
  <mtu size="1400"/>
</interface>

HotPlug

anchorvm plugs the NIC into an existing domain, live and persistent. On delete it detaches only that NIC. Nothing else of the domain is touched.

spec:
  hypervisor: os-aio
  network: {nad: shadow-lab/shadow-net, subnet: shadow-subnet}
  attach: {mode: HotPlug, domain: web1}

Day-2 operations

To do thisRun or edit
Change security groupsspec.network.securityGroups (applied live)
Change per-port DHCP optionsspec.network.dhcpV4Options, e.g. mtu=1300
Remove a NICkubectl delete vmport …
Remove a NIC whose hypervisor is deadkubectl annotate vmport … anchorvm.io/force-delete=true. The agent removes the leftover tap when it comes back.
OVN lost the port (database restore)kubectl annotate vmport … anchorvm.io/repair-network=true. Kube-OVN re-creates it with the same IP and MAC.

These fields cannot be changed after creation, and the API rejects edits: hypervisor, nad, subnet, ip, mac, attach.

Safety rules

  1. Anchor pods can't be broken by accident. An admission policy denies deleting, evicting, un-gating or editing anchors for anyone except the anchorvm controller and Kube-OVN. Kube-OVN frees a pod's IP the moment the pod is marked for deletion, and a finalizer cannot stop that, so prevention is the only safe option.
  2. Unique names per instance. The anchor is av-<vmport>-<uid8> and the tap is av plus a hash of the VMPort UID. A VMPort recreated with the same name gets a new OVN port, so a leftover tap on a dead host can never take it over.
  3. No duplicate IPs. If two VMPorts ask for one IP, the older wins and the other shows IPConflict. If a VMPort asks for a pod's IP, Kube-OVN refuses. IPs are never reassigned automatically.
  4. Agents are fenced like kubelets. Each hypervisor has its own identity. It may only write status.agent, and only for VMPorts on its own host.
  5. The agent's cleanup is careful. It removes only taps it tagged itself, only after the API (not a cache) reports the VMPort gone on two passes a minute apart, and it never touches domains or disks.
  6. A stuck delete never resolves itself. Guessing could free an IP that is still in use, so it waits for a person.
  7. Kube-OVN upgrade guard. anchorvm relies on Kube-OVN behaviour that is not a documented API. New VMPorts are refused on an untested Kube-OVN version until the e2e suite has been re-run.

What was tested

48 / 48 live checks passed on train (Kubernetes v1.33, stock Kube-OVN v1.16.0) and hypervisor os-aio (libvirt 10.0, OVN 25.03), run on 2026-10-22 with test/e2e.sh. The test script plays the platform: it creates throwaway CirrOS VMs that use the taps anchorvm provides.

Also observed live: 19 unit tests (controller and agent) pass; the anchor model kept every VM reachable (0 lost pings in about 500 samples) through two kube-ovn-controller restarts, an ovn-central restart and a 30-second GC interval run by other tests on the same cluster.

The first run had 4 failures. Three were a bug in the test script (it treated a correct denial as a failure) and one was a test that never force-deleted a VMPort whose hypervisor has no agent, which anchorvm correctly refused to delete on its own. Both were fixed in the test; no product change was needed.
